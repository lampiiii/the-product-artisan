How I Actually Use Claude Code

I run two operating systems on Claude Code — a personal PM workspace and a team-wide one — both entirely markdown and Git, no Notion or Jira. Skills, agents, hooks, and a directory-scoped CLAUDE.md system do the work a stack of SaaS tools usually does.

Everything below is real and verifiable — pulled directly from my public and private repos, generalized where the original was scoped to a specific product domain.

The Big Idea
I treat Claude Code as a team operating system, not a coding assistant. Everything — specs, notes, generated dashboards, slash commands, agents, hooks — lives in one Git repo. The repo is the context: Claude Code reads from it, writes to it, and keeps it coherent. A well-organized repo with strong CLAUDE.md files works the same way a well-documented codebase does for a new engineer.

Deterministic automation at the harness level — no LLM involved, no chance of forgetting. My rule: if I find myself repeating an instruction every session, it belongs in a hook, not in memory.

Guardrails
Permission hardening at the harness level, so the model asks instead of guessing.
Destructive commands are denied outright in settings.json — rm -rf, sudo rm, git push --force, git reset --hard. The model can't accidentally run them; it has to ask me instead. I can always approve one explicitly when I mean it — I can't un-run one I didn't.
CLAUDE.md Governance System
Every folder gets a CLAUDE.md answering three questions: what is this folder for, what belongs here, and what doesn't (and where does it go instead). The root CLAUDE.md has a routing table — a decision tree mapping any content type to its correct home, so Claude almost never files something in the wrong place. 50 files total across my personal and team-wide systems, loaded in order: global user settings → project root → folder-level.

How I Work
A few habits that keep a long-running Claude Code practice from degrading over time.
Scoped reading
I tell Claude to read only what it needs. @file mentions pull specific files in rather than hoping Claude finds them; skills declare which repo files they should read in their own frontmatter.
/compact and /clear discipline
/compact when continuing the same topic (keeps the summary, drops the raw transcript); /clear on a genuine topic shift. The nudge-compact hook reminds me before I'd otherwise think to.
Plan Mode for anything non-trivial
Multi-file changes or non-obvious sequencing go through Plan Mode first — Claude lays out the full plan before touching anything, catching "that's not what I meant" before edits land.
Fresh agents for review
Critic and QA agents always run in a fresh sub-agent context. An author reviewing their own work has anchoring bias; a fresh context doesn't.
What I'd Recommend to Anyone Starting
1
Write CLAUDE.md before you write anything else. A repo Claude Code can navigate confidently is worth more than dozens of individual prompts. Think of it as the README your AI colleague reads every session.
2
Put recurring behavior in hooks, not in memory. If you're repeating an instruction every session, it belongs in a hook or a CLAUDE.md. Memory is for facts; hooks are for behavior.
3
Deny the dangerous commands up front. Add rm -rf, git push --force, and git reset --hard to the deny list. You can always approve them explicitly when you mean to; you can't un-run them when you didn't.
4
Use separate agents for creation and critique. Don't ask the same context window that wrote a document to also review it. Spawn a fresh critic agent — it finds things the author context missed.
5
Log everything, polish selectively. Auto-capture every session with a Stop hook. Polish the entries that matter with a manual command. A complete record, without the overhead of journaling by hand.
6
Treat the repo as the source of truth, not the conversation. Anything important that comes out of a session should land in the repo — a file, a YAML update, a JSON entry. The conversation is ephemeral; the repo is not.
