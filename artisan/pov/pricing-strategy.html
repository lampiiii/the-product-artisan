Pricing Strategy

AI compute cost is a per-call, per-user variable cost that scales with adoption — a cost-of-goods-sold input, not a rounding error. Treating it that way is a pricing decision as much as an engineering one.

Compute Cost Is a Unit-Economics Problem Now
Traditional software features cost roughly the same to serve whether one user or a thousand use them. A GenAI feature that calls a large language model on every interaction doesn't work that way — every single use has a real, variable cost attached. That changes what "just ship it" means: a feature that looks free to use can be quietly unsustainable at scale. Recognizing that, and designing around it before the bill arrives, is unit-economics thinking applied directly to product architecture — not a finance team's problem to catch after launch.
Cache First, Regenerate Deliberately
A GenAI insight-generation feature within the Customer Success Management product line was heading toward a pattern where every page view triggered a fresh LLM call — cost scaling linearly with usage, with no ceiling. The fix was a cache-first architecture with a deliberately bounded regeneration path:

Two Surfaces, Two Deliberate Answers
A second, related GenAI surface in the same product area kept a simpler daily-regeneration model instead of adopting the cache-and-refresh pattern — because it's lower-volume and more trigger-driven, and daily generation is still affordable there. Same underlying cost concern, two different chosen answers, based on each surface's actual volume and value — not one uniform policy applied everywhere for convenience. That's the pricing-strategy instinct: match the cost model to the economics of the specific surface, not to what's easiest to build once.
The Operating Principle
The line that drove the whole redesign: you can't push unconstrained compute cost onto the customer. Whatever a GenAI feature costs to run has to be designed for up front — through caching, bounded context windows, explicit expiry, and a cadence chosen deliberately by volume — the same way a packaging or SKU decision would be, not bolted on reactively once the bill arrives.
A feature that's technically "free" to the user but unbounded in compute cost isn't a pricing problem for later — it's a pricing decision being made by default, right now, by whoever wrote the architecture. Owning that decision on purpose is the job.
