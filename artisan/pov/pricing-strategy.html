Pricing Strategy

Running AI costs real money every time it's used, and that cost grows as more people use the feature — it's a direct cost of running the product, not a rounding error. Treating it that way is as much a pricing decision as an engineering one.

The Cost of Running AI Scales With Usage
Traditional software features cost roughly the same to run whether one person or a thousand use them. An AI feature that calls a language model every time someone uses it doesn't work that way — every single use has a real cost attached. That changes what "just ship it" means: a feature that looks free to use can quietly become too expensive to sustain as it grows. Recognizing that, and designing around it before the bill arrives, means treating cost-per-use as a real design input — not a finance team's problem to catch after launch.
Reuse Results First, Regenerate Only When Needed
An AI insight feature in the Customer Success product was heading toward a pattern where every single page view triggered a fresh, costly AI call — with cost rising in a straight line as usage grew, and no limit in sight. The fix was to save and reuse previous results, with clear limits on when a fresh one gets generated:

Two Similar Features, Two Different Answers
A second, related AI feature in the same product area kept a simpler daily-refresh approach instead of adopting the same save-and-reuse pattern — because it's used less often and driven by specific triggers, so daily generation is still affordable there. Same underlying cost concern, two different answers chosen based on each feature's actual usage and value — not one uniform rule applied everywhere for convenience. That's the core pricing instinct: match the cost approach to the specific feature's economics, not to whatever's easiest to build once.
The Operating Principle
The idea that drove the whole redesign: you can't pass unlimited AI running costs onto the customer without a plan. Whatever an AI feature costs to run has to be designed for up front — through reusing results, limiting how much data feeds each request, setting clear expiry times, and choosing a refresh rate based on actual usage — the same way you'd think through pricing and packaging, not bolted on reactively once the bill arrives.
A feature that looks "free" to the user but has no limit on what it costs to run isn't a pricing problem for later — it's a pricing decision being made by default, right now, by whoever built it. Owning that decision on purpose is the job.
