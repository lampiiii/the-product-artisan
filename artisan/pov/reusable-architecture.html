Reusable Architecture

One consistent way of organizing work, applied the same way across five product lines and 100+ features — not a different process per team, and not one-off solutions rebuilt from scratch every time.

One Single Source of Truth Per Feature
Every feature — 100+ of them, across every product line — maps to exactly one file that lists: owners across product, engineering, design, and research; current status and target date; every linked item in the team's work-tracking system; and any related team communication channel. This one file is what every dashboard, every automation, and every teammate reads from — there's no second copy of the truth to keep in sync.
The Same Folder Shape, Every Feature
A feature's lifecycle runs through the same five stages regardless of which product line it belongs to — so a new teammate can navigate any feature in the system without being told where to look.
Inputs Designs, research, meeting notes, feasibility findings, reference docs
Spec The PRD and any prototypes, pre-handoff
Shipped Release notes, explicit scope-cut documentation, tech specs, real UI screenshots
Handoff Cross-team docs so other teams don't need a live meeting for context
Backlog Running "what's next" — carries forward anything cut or newly requested
One Simple Rule Decides Where Anything Goes
Not everything is a feature. One simple set of questions decides where any new piece of content belongs, so the system can't slowly turn into a dumping ground: is this about one specific feature? Product-wide context, like roadmap or customers? Product-wide reference material, like architecture or data structure? Team-wide reference material, like the design system? Is it about people, a repeatable practice, a recurring team review, or the platform itself? Each answer points to exactly one folder — "where does this go" always has one right answer, not a fresh judgment call each time.
Automatically Set Up, Never Rebuilt by Hand
The folder structure above is never assembled manually. One shortcut instantly creates a new feature's full folder set, already filled in with its core file; another creates a new dated instance of a recurring team review — the same setup every cycle, never rebuilt from scratch; and a third can automatically sort an entire product's existing backlog into this structure, grouping existing work into features — and it's safe to run more than once, so it never creates duplicates of work already sorted.
Built Once, Reused Across Every Product Line
70+ skills and roughly 30 specialized agents live in shared buckets (Research, PRD Authoring, Planning & Records, Communications, Presentations, Design & Prototyping) rather than being rebuilt per team — every product line draws from the same library instead of improvising its own process. Full breakdown of each bucket on Platform Thinking →
Reusable Doesn't Mean Unmaintained
Two disciplines keep the library from drifting or shipping half-finished:
A shared foundation, loaded first
Every design-related tool loads a common set of building blocks (colors, components, accessibility rules) before creating anything — so results stay consistent with each other instead of drifting apart over time.
Unfinished parts are labeled, not hidden
Several newer pieces are clearly marked as not-yet-confirmed and require someone to sign off before they're allowed to go live — the system never silently presents half-built work as finished.
Also Shown Outside the Day Job
Shared primitives, not per-screen copies
Recomp's cross-cutting UI (a shared bottom-sheet host, toast system) and data access layer are built once and reused across every feature screen — the daily-checklist, workout-log, meal-log, and voice-log screens all pull from the same primitives instead of each rolling its own.
The best system isn't the one that solves today's feature — it's the one where the 104th feature is just as easy to set up as the 1st. Every part of this — the records, the folder structure, the setup shortcuts — is designed to work across all product lines, not just one.
