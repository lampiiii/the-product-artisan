Reusable Architecture

One information architecture, applied identically across four product lines and 73 features — not a bespoke process per team, and not one-off solutions rebuilt from scratch every time.

One Canonical Record Per Feature
Every feature — all 73 of them, across every product line — maps to exactly one structured metadata file: owners across PM, engineering, design, and research; current status and target date; every linked item in the team's internal work-tracking system; and any linked team communication channel. This single file is the join point every dashboard, every automation, and every teammate reads from — there's no second source of truth to keep in sync.
The Same Folder Shape, Every Feature
A feature's lifecycle runs through the same five stages regardless of which product line it belongs to — so a new teammate can navigate any feature in the system without being told where to look.
Inputs Designs, research, meeting notes, feasibility findings, reference docs
Spec The PRD and any prototypes, pre-handoff
Shipped Release notes, explicit scope-cut documentation, tech specs, real UI screenshots
Handoff Cross-team docs so other teams don't need a live meeting for context
Backlog Running "what's next" — carries forward anything cut or newly requested
Scaffolding, Not Copy-Paste
The folder shape above is never assembled by hand. A scaffolding command instantly creates a new feature's full skeleton, pre-populated with its canonical metadata file; another creates a new dated instance of a recurring ceremony — same input-to-deck pipeline every cycle, never rebuilt from scratch; and a third can bootstrap an entire product's existing backlog into this structure automatically, grouping already-existing work into features — and it's safely idempotent, so re-running it never duplicates anything already mapped.
Built Once, Reused Across Every Product Line
70+ skills and roughly 30 specialized agents live in shared buckets rather than being rebuilt per team — every product line draws from the same library instead of improvising its own process.

Shared design-system foundation loaded by every design skill
Reusable Doesn't Mean Unmaintained
Two disciplines keep the library from drifting or shipping half-finished:
A shared foundation layer, loaded first
Every design-related skill loads a common foundation (design tokens, components, accessibility rules) before generating anything — so outputs stay consistent with each other instead of drifting apart over time.
Stubs are labeled, not hidden
Several newer pieces are explicitly marked as unconfirmed stubs and gated behind an ownership-confirmation step before they're allowed to go live — the platform doesn't silently present half-built capabilities as finished.
The best architecture isn't the one that solves today's feature — it's the one where the 74th feature costs the same to onboard as the 1st. Every canonical record, folder shape, and scaffolding command here is designed to compose across product lines, not just work for one.
