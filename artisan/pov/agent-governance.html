Agent Governance

Deciding who — person or AI agent — is allowed to use which AI capability, under what conditions, with what data access, and what happens if the rules themselves break. This is a working safety system that an 80+ person team relies on every day, not a policy document nobody reads.

Governance Is a Design Decision, Not a Wrapper
Once a team is using dozens of specialized AI agents instead of one chatbot, "should this person or agent be allowed to do this, with this data, right now?" becomes a real question that needs a real answer — the same problem any shared software system has to solve, just with an AI in the loop instead of only people. I designed and built that safety layer for a platform with roughly 70 AI capabilities.
The Risky Way
Anyone Can Use Anything
Whoever can type a request can use any AI capability with any data — fine for a demo, unsafe once a whole team relies on it
What I Built Instead
Check Identity, Then Grant Access
Every request is checked against who's asking, and if anything is unclear, access is denied by default
Two Access Levels, and a Deliberate Third "Unknown" State
Every request lands in one of two groups: a small set of trusted people (core), or everyone else by default (consumer). But the design goes one step further — if someone's identity can't be confirmed at all, they don't default to "everyone else." They land in a separate unknown state that is always denied. Most security holes happen at these edge cases; this system treats "I can't tell who this is" as the most locked-down case, not a shrug.
When in doubt, deny — every time
Unknown person, unknown AI agent, unclear access level, missing permission — every one of these results in "no," never "yes." The system never guesses in favor of letting something through.
Access level isn't something you can just request
Who has which access level is set centrally in one file, kept separate from the regular team roster — so updating "who's on the team" can never accidentally change what anyone is allowed to do.
One Main Entry Point, With Rare Approved Exceptions
Most specialized AI agents can't be reached directly by a regular user — a request first goes through one central point that figures out what's actually needed and hands it off to the right agent. A specific agent can be pre-approved for direct access in rare cases, but that's an exception someone has to explicitly turn on, not the default. This means the path a request takes is controlled, not just what it's allowed to touch at the end.
A routing stamp that can't be faked
When the central entry point hands a request off, it attaches a marker that the receiving agent checks for. A request can't just claim it came through the right path — the marker actually has to be there.
Unlisted agents simply can't be reached
If an AI capability isn't on the approved list, nothing can reach it — no access level and no routing path gets you there. There's no "allow it if you're not sure" fallback anywhere.
Data Access Is Governed Independently of Routing
Being allowed to use an AI agent and being allowed to see the data it touches are two separate checks. Every capability sits at one of three levels — everyone can see it (public), only your access level determines it (private), or nobody sees it by default (vault). Even a trusted person is denied vault-level data unless they've been individually and explicitly granted access to that exact piece of data — access is never assumed just because someone is generally trusted.
Two Kinds of Failure, Handled on Purpose Differently
Not every failure should be handled the same way — treating them identically is its own bug. This system draws a sharp line between the safety-rules file being missing versus being present but broken:
Rules File Missing
Rules File Present but Corrupted
Stays open — AI agent requests still go through
Locks down — all AI agent requests get blocked
Treated as a simple setup mistake — shouldn't break the whole platform for everyone
Treated as possible tampering — a broken safety check must never silently stop working
Getting this backwards is a common real-world mistake: either the platform breaks over a routine typo, or a corrupted rules file quietly turns off protection for everyone. Handling these two failure types differently, on purpose, is the actual work.
The Safety Rules Protect Themselves
A short, specific list of the files that define these safety rules can only be edited by someone in the trusted core group. Anyone outside that group cannot edit the rules that grant access — including the file that decides who's trusted in the first place. Without this, the whole system would just be a suggestion anyone with edit access could quietly switch off.
Every Decision Leaves a Record
Every single AI agent request — whether allowed or blocked — gets logged: who asked, what access level they had, whether it went through the right entry point, the decision, and why. "The AI did something" stops being a mystery and becomes something anyone can look up afterward.
A backup check on who gets mentioned
A separate check runs on every document before it's saved: if it mentions a teammate who isn't actually on the current team list, the save is blocked — preventing an outdated or mistyped name from ever reaching a real document.
A Person Always Signs Off, Built Into the Process
Access control is just the baseline. On top of it, the actual multi-step workflows on this platform have specific points where a human has to step in and approve — not as an afterthought, but as a required step the automation cannot skip past.
A required human decision partway through
The process that turns a customer problem into a requirements document stops partway and requires a person to make a specific classification call before it continues — the AI can't decide that on its own.
A scored quality check before handing off to engineers
Every requirements document has to pass a structured, multi-part quality review before it's considered ready to hand off — not just a spellcheck, a real pass/fail check.
Research findings are never published automatically
New research findings wait for a research lead to review and approve them before they're shared anywhere else.
A rejected draft doesn't leave a mess behind
Every AI agent that adds to the shared research library — customer profiles, use cases, glossary terms, open questions — submits a pending suggestion only. A permanent ID is only created once a human approves it, so a rejected draft doesn't leave a broken reference behind.
Nothing external sends itself
Every drafted email or chat reply is exactly that — a draft. It never sends without a person explicitly clicking send, no matter how confident the AI is.
Updates to shared team records need confirmation
Any update to the team's internal work-tracking system requires an explicit confirmation step first — nothing gets silently written to records the whole team relies on.
Governance Components, Mapped
Component What It Ensures Why It's Hard to Get Right
Identity checks Deny when unclear An identity that can't be confirmed must never be treated as trusted
Central entry point Control the path, not just the destination Being allowed to use something and being able to reach it directly are different guarantees
Three-tier data access Minimum necessary access The most sensitive data needs an explicit, named permission — never an assumption
Different failure responses Handle each failure type on purpose A simple mistake and a broken/tampered system need opposite default responses
Self-protected rules files Rules can't edit themselves A rule that can quietly change itself isn't a rule
Complete activity log Accountability Every allow/deny decision needs a reason someone can review later
Human sign-off points Keep a person in the loop by design Automation should speed up judgment calls, not replace the person making them
Good governance for AI isn't a policy document bolted on after launch — it's a set of decisions made up front about who can do what, what happens when the rules break, and where a human has to stay in the loop. That's the part of the work that agents themselves cannot do for you.
