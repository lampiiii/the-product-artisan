Agent Governance

Defining who — and what — is allowed to call which AI agent, under what conditions, with what data access, and what happens when the rules themselves fail. This is the governance layer for a real multi-agent system a 61-person team uses daily, not a policy document nobody reads.

Governance Is a Design Decision, Not a Wrapper
Once a team has dozens of specialized AI agents instead of one chatbot, "can this caller invoke this agent, with this data, right now?" stops being a hypothetical and becomes a real access-control problem — the same shape as any multi-tenant system, just with a model in the loop instead of a person. I designed and built that layer for a platform roughly 70 capabilities deep.
Naive Approach
Any Caller, Any Agent
Whoever can type a prompt can invoke any capability with any data — fine for a demo, unsafe at team scale
What I Built
Resolved Role, Explicit Grant
Every call resolves to a role, checks a registry entry, and defaults to deny on anything ambiguous
Two Roles, and a Deliberate Third State
Every caller resolves to core (a small set of trusted authors) or consumer (everyone else, by default). But the design doesn't stop there — an identity that can't be resolved at all doesn't fall back to "consumer," it becomes its own unknown state and is always denied. Most access-control bugs happen at the edges; this system treats "I couldn't figure out who you are" as the least permissive case, not a shrug.
Most-restrictive-on-ambiguity, as a running principle
Unknown caller, unknown agent, unresolved role, missing grant — every one of these resolves to deny, never to allow. The system never guesses permissive.
Role isn't a permission set someone can request
Roles are assigned centrally in a policy file, deliberately separate from the org roster — so editing the "who's on the team" list can never silently change what anyone is allowed to do.
One Front Door, Explicit Side Doors
Most specialized agents aren't directly callable by a general user — a request has to be routed through a single orchestrating front door, which resolves what's actually needed and dispatches to the right capability. An agent's registry entry can explicitly whitelist which roles may call it directly (a "side door"), but that's an opt-in exception per agent, not the default. This keeps the access path itself governed, not just the destination.
A routing signal the model can't forge in normal operation
When the front door routes a request onward, it stamps the outgoing call with a marker the receiving gate checks for. A caller can't just claim to have been routed — the marker has to actually be present.
Unregistered agents are unreachable, period
If a capability isn't in the registry at all, no role and no routing path can reach it — there's no fallback "allow if unsure" branch anywhere in the decision logic.
Data Access Is Governed Independently of Routing
Being allowed to call an agent and being allowed to see the data it touches are two separate checks, evaluated independently. Every capability sits at one of three tiers — public, private, or vault. The first two follow the caller's resolved role; vault is fail-closed by design — denied by default even for an otherwise-trusted role, unless a specific, named grant exists for that person and that exact resource. Vault access is opt-in per person, never assumed from role alone.
A Deliberately Asymmetric Fail Posture
Not every failure should behave the same way, and treating them identically is its own bug. This system draws a sharp line between a missing configuration and a present-but-broken one:
Config File Missing
Config File Present but Corrupted
Fails OPEN — agent calls proceed
Fails CLOSED — all agent calls blocked
Read as a misconfiguration — shouldn't brick the platform for everyone
Read as possible tampering — a broken gate must never silently stop enforcing
Getting this distinction backwards is a classic real-world governance failure: either the platform becomes unusable on a routine typo, or a corrupted policy file quietly turns off enforcement for everyone. Designing for both failure modes, differently, on purpose, is the actual work.
A Self-Protecting Policy
A short, explicit list of the governance system's own configuration and enforcement files can only be edited by a core-role caller. A consumer cannot edit the rules that grant access — including the file that assigns roles in the first place. Without this, "governance" is just a suggestion anyone with edit access could quietly turn off.
Every Decision Leaves a Trace
Every single agent invocation — allowed or denied — is appended to an audit log: who called it, what role they resolved to, whether the call was routed through the front door, the decision, and the reason. "The AI did something" stops being a black box and becomes something you can actually reconstruct after the fact.
Handle validation as a companion control
A separate check runs on every document before it's written: if it @-mentions a teammate who isn't on the live roster, the write is blocked — preventing a stale or typo'd mention from ever reaching a real document.
Human Sign-Off, Baked Into the Pipelines
Access control is the floor, not the whole system. On top of it, the actual multi-step workflows built on this platform have explicit human checkpoints designed in — not as an afterthought, but as a required step the automation cannot skip.
A required classification decision, mid-pipeline
A "problem to requirements doc" pipeline stops partway through and requires an explicit human classification call before it will continue drafting — it can't talk itself into a category on its own.
A scored fidelity check before engineering handoff
Any requirements doc has to clear a multi-dimension scored review before it's considered ready to hand off — not just a spellcheck, a structured pass/fail gate.
Research insights are never auto-published
Newly synthesized research findings sit for explicit review and approval by a research lead before they're published anywhere else in the system.
Nothing external sends itself
Every drafted email or chat reply is exactly that — a draft. It is never sent without an explicit human clicking send, regardless of how confident the draft is.
Writes to the system of record require confirmation
Any write to the team's internal work-tracking system requires an explicit confirmation step before it happens — no silent writes to shared, load-bearing records.
Governance Components, Mapped
Component Governance Principle Why It's Hard to Get Right
Role resolution Deny on Ambiguity An unresolvable identity must never read as permissive
Front-door routing Access Path Control Being callable and being reachable are different guarantees
Three-tier data access Least Privilege Vault-tier data needs an explicit, named grant — never an inference
Fail-open vs. fail-closed Asymmetric Failure Design Misconfiguration and tampering need opposite default behaviors
Self-protected policy files Policy Integrity A rule that can edit itself isn't a rule
Append-only audit log Accountability Every allow/deny needs a reason someone can review later
Human sign-off gates Human-in-the-Loop by Design Automation should accelerate judgment, not replace the point where it's needed
Governance isn't a policy doc bolted onto an AI system after launch — it's a set of design decisions made up front about who can do what, what happens when the rules break, and where a human has to stay in the loop. That's the work agents themselves cannot do for you.
